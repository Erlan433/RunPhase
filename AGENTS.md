# RunPhase: правила проекта

## Цель продукта

- RunPhase — мобильный интервальный таймер для бега, рассчитанный на последующую упаковку в Android через Capacitor.
- Основной сценарий: настройка тренировки → выполнение с минимальным числом элементов на экране → результат.
- Тренировка строится строго в порядке: разминка → повторяющиеся фазы бега и ходьбы → заминка → результат.
- Настраиваемые значения: длительность разминки, бега, ходьбы и заминки, а также количество циклов.

## Технологические ограничения

- Использовать только HTML, CSS и Vanilla JavaScript.
- Не добавлять React, Vue, Angular, UI-библиотеки, CSS-фреймворки и готовые UI-шаблоны.
- Не вводить сборщик, фреймворк или сложную архитектуру без подтвержденной необходимости.
- Приложение должно полностью работать без интернета; основные функции не должны зависеть от CDN, API или удаленных ресурсов.
- Все необходимые шрифты, иконки, звуки и другие ресурсы хранить локально либо реализовывать средствами HTML/CSS/SVG.
- Сохранять совместимость с мобильным WebView и будущей оболочкой Capacitor; не связывать доменную логику с браузерным или нативным API напрямую.

## Архитектура и код

- Предпочитать небольшое число понятных файлов и модулей; не создавать абстракции «на будущее».
- Разделять состояние тренировки, расчет последовательности фаз, ход таймера, хранение настроек и отображение интерфейса.
- Последовательность фаз формировать из пользовательских параметров, а не прописывать вручную в разметке.
- Использовать одну явную модель состояния с фазами настройки, активной тренировки, паузы, завершения и результата.
- Таймер рассчитывать по фактически прошедшему времени, а не только по количеству вызовов `setInterval`, чтобы снизить накопление ошибки при блокировке экрана или работе приложения в фоне.
- Валидировать ввод и корректно обрабатывать нулевые длительности, минимальное/максимальное число циклов, паузу, продолжение, перезапуск и досрочное завершение.
- Настройки сохранять локально. Не собирать аналитику и не отправлять пользовательские данные без отдельного требования.
- Имена в коде писать на английском; пользовательский интерфейс и тексты продукта по умолчанию — на русском.

## Интерфейс и визуальный язык

- Создавать оригинальный минималистичный спортивный интерфейс, не копируя существующие приложения.
- Использовать темный фон, лаймовый акцент для бега и синий для ходьбы.
- Разминка, заминка и нейтральные состояния должны визуально отличаться, но не конкурировать с основными акцентами.
- Главный визуальный элемент — маршрут тренировки из сегментов разминки, бега, ходьбы и заминки; он должен одновременно показывать структуру и текущий прогресс.
- Во время тренировки показывать только необходимое: текущую фазу, оставшееся время, прогресс/маршрут и основные действия управления.
- Использовать крупную типографику, достаточный контраст и удобные для касания элементы размером не менее 44×44 CSS-пикселей.
- Цвет не должен быть единственным способом различения фаз: добавлять понятные подписи и, при необходимости, форму или паттерн.
- Учитывать безопасные зоны мобильных устройств, портретную ориентацию, узкие экраны и системную настройку уменьшения движения.

## Поведение тренировки

- Один цикл состоит из фазы бега, за которой следует фаза ходьбы; количество циклов определяет число таких пар.
- После последней ходьбы начинается заминка, затем показывается результат.
- Переходы между фазами должны быть заметны без постоянного взгляда на экран; звуковые и вибрационные сигналы проектировать как локальные и отключаемые.
- Экран результата должен опираться на реально выполненную тренировку и не выдумывать метрики, для которых нет данных.

## Качество и процесс

- Сначала уточнять поведение и состояния, затем реализовывать минимальный рабочий сценарий; дополнительные функции добавлять только по явному запросу.
- Не добавлять авторизацию, облачную синхронизацию, социальные функции, GPS, карты или серверную часть без отдельного требования.
- Проверять логику последовательности и таймера отдельно от DOM, а ключевой сценарий — вручную на узком мобильном экране.
- После изменений проверять офлайн-запуск, отсутствие сетевых зависимостей, клавиатурную доступность и основные состояния таймера.
- Не изменять пользовательские файлы и решения вне текущей задачи; новые зависимости и архитектурные усложнения предварительно обосновывать.
